# Contributing

Thank you for your interest in contributing to Krunixbase Debugger.

This project is part of the Krunixbase Ecosystem and aims to provide deterministic debugging, diagnostics, monitoring, and observability components for modern applications.

---

## Before Contributing

Please read:

- README.md
- SECURITY.md
- CODE_OF_CONDUCT.md

before opening issues or submitting pull requests.

---

## Ways to Contribute

Contributions are welcome in the following areas:

### Documentation

Examples:

- Architecture documentation
- Integration guides
- API references
- Troubleshooting guides

### Bug Reports

Useful bug reports include:

- Clear description
- Steps to reproduce
- Expected behavior
- Actual behavior
- Environment details

### Feature Requests

Feature requests should explain:

- The problem being solved
- The proposed solution
- Expected benefits
- Possible implementation ideas

### Code Contributions

Examples:

- Diagnostics collectors
- Monitoring modules
- Framework adapters
- Test coverage improvements
- Performance optimizations

---

## Development Principles

All contributions should follow the project's core principles:

### Determinism

Behavior should be predictable and reproducible.

### Simplicity

Avoid unnecessary complexity.

### Security

Security considerations should be included during design and implementation.

### Transparency

Code should be understandable and maintainable.

### Reliability

Components should fail gracefully and provide useful diagnostics.

---

## Development Workflow

1. Fork the repository.
2. Create a feature branch.
3. Make changes.
4. Test changes locally.
5. Update documentation if necessary.
6. Submit a Pull Request.

Example:

```bash
git checkout -b feature/websocket-diagnostics
```

---

## Commit Messages

Use clear commit messages.

Examples:

```text
feat: add websocket diagnostics collector

fix: resolve event bus listener leak

docs: update architecture overview

test: add debugger unit tests

refactor: simplify error handler
```

---

## Pull Requests

Pull requests should:

- Focus on a single topic
- Include a clear description
- Pass available tests
- Include documentation updates when applicable

---

## Documentation Requirements

Changes affecting:

- Architecture
- Public APIs
- Diagnostics behavior
- Security mechanisms

should include documentation updates.

---

## Security Contributions

Security-related reports should follow the guidelines described in SECURITY.md.

Please avoid publicly disclosing vulnerabilities before maintainers have had an opportunity to review them.

---
